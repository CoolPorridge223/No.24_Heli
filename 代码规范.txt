================================================================================
          MC 直升机模组 · 代码规范（AI 协作强制版 / 人类开发者同样适用）
================================================================================

适用项目：Minecraft 直升机模组（Helicopter Mod）
运行环境：Minecraft 1.21.1 / Fabric 0.19.2（以 gradle.properties 实际声明为准）
语言与映射：Java 21 / Yarn Mappings
执行对象：GPT-6 系列编码模型（首要）、项目所有开发者

--------------------------------------------------------------------------------
第 0 章  给 GPT-6 模型的硬性行为准则（最高优先级，先读再动手）
--------------------------------------------------------------------------------

0.1  最小改动原则。只完成本次被要求的内容，禁止顺手重构、改名、调格式、
     挪动无关代码、“优化”没让你动的地方。
0.2  禁止过度工程。不提前抽象，不引入没被要求的接口、工厂、单例、事件总线
     包装、配置类、设计模式。第二次出现重复代码时才允许提取，且只提取当前
     用得到的部分。
0.3  禁止防御性烂代码。不为逻辑上不可能发生的情况堆 null 检查、try-catch、
     兜底分支。仅在以下“系统边界”做必要校验：网络包接收、存档/NBT 读取、
     玩家输入、跨端调用。校验失败要给出明确结果（丢弃并记录日志），禁止
     静默吞异常。
0.4  禁止在项目里“拉屎”。临时测试类、临时 main 方法、调试用 System.out、
     注释掉的旧代码、临时脚本、测试存档、截图、导出的日志，用完必须当场
     删除。任务完成后 git status 中不允许出现任何与需求无关的文件。
0.5  项目长期不保留测试目录、不保留测试用例。测试是一次性验证手段，不是
     交付物（详见第 8 章）。
0.6  不确定的 Yarn 映射名、类名、方法签名，先查项目现有代码或官方映射，
     禁止凭记忆编造 1.21.1 中不存在的 API。引用 MC 类必须写全限定名。
0.7  严格区分三端：物理客户端（CLIENT）、逻辑服务端（SERVER）、集成服务端。
     客户端类必须标注 @Environment(EnvType.CLIENT)；飞行物理、伤害、库存
     等权威逻辑只允许在服务端执行。
0.8  非必要不修改 gradle.properties、build.gradle，不允许新增依赖，如果需要更新版本号，则可以直接修改前两个文件，否则的话，除非任务
     明确要求并说明理由，那就非必要不改动
0.9  新增任何文件前，先在第 6 章的包结构中找到它的归属；找不到归属，说明
     这个文件可能不该存在，先提问而不是硬建。
0.10 全部注释使用中文（MC 类名、方法名、标识符保持英文原样）。
0.11 每次任务完成前必须执行第 9 章的验证流程，并在交付说明中写明执行了
     什么、结果如何。
0.12 需求有歧义且会影响实现方向时，一次性列出问题再动手；不影响方向的
     细节自行决定，并在注释或交付说明中注明。
0.13 禁止生成本规范第 10 章规定之外的任何文档文件（如 CHANGELOG.md、
     TODO.md、NOTES.txt、测试说明.md 等）。
0.14 模型不得在代码注释、提交信息、文档中留下“由 AI 生成”之类的署名。


--------------------------------------------------------------------------------
第 1 章  项目基本约定
--------------------------------------------------------------------------------

1.1 模组 ID（mod id）：全小写、下划线分词，在主类中以常量 MOD_ID 声明，
    所有注册名、网络通道、配置键统一使用该 ID，禁止散落字符串字面量。
1.2 注册名规则：全小写 + 下划线，见名知义，例如 helicopter、
    helicopter_entity、joystick_item。
1.3 1.21.1 标识符构造使用 Identifier.of(MOD_ID, "path")，禁止使用已废弃的
    new Identifier(...) 写法。
1.4 主类只做模组生命周期初始化与注册转发，不写业务逻辑；业务逻辑按第 6 章
    分包。
1.5 静态注册表（物品、实体类型、方块、声音事件等）集中在对应的 ModXxx
    注册类中统一注册，禁止在各处零散 Registry.register。
1.6 日志统一使用 SLF4J（LogUtils.getLogger() / LoggerFactory.getLogger()），
    禁止 System.out / System.err / printStackTrace。


--------------------------------------------------------------------------------
第 2 章  注释规范（本项目核心要求，必须逐条做到）
--------------------------------------------------------------------------------

2.1 总原则
    (1) 注释解释“为什么这么写、边界是什么、出了问题怎么查”，而不是把
        i++ 翻译成“i 加一”。
    (2) 每一个类、接口、枚举、方法（含 private）和关键字段都必须有注释。
    (3) 凡引用 Minecraft / Fabric API，必须写出全限定名（或在 JavaDoc
        {@link} 中写全），并说明该 API 在本处的作用，不允许只写“调用 MC
        方法”这种废话。
    (4) 注释必须随代码同步修改；改逻辑不改注释等同于未完成。

2.2 文件头注释（每个 .java 文件顶部）
    必须包含：文件职责一句话说明、所属端侧（CLIENT / SERVER / COMMON）、
    关联的注册名或网络通道（如有）。模板：

    /**
     * 文件：直升机实体类，负责载具的注册属性、飞行物理与乘降逻辑。
     * 端侧：COMMON（逻辑服务端权威，客户端仅做渲染插值）。
     * 注册名：helicopter:helicopter_entity
     */

2.3 类 / 接口 / 枚举注释
    必须包含五部分：
    ① 职责：这个类是干什么的；
    ② 引用的 MC / Fabric 库：列出关键依赖类的全限定名及用途；
    ③ 生命周期 / 调用时机：谁实例化它、谁每 tick 调它、何时注册；
    ④ 端侧与线程：运行在客户端还是服务端、是否在渲染线程；
    ⑤ 常见问题排查：本类最容易出错的 2~4 个现象及定位顺序。

2.4 方法注释（JavaDoc，强制模板）
    /**
     * 功能：一句话说明方法做什么（说明“做什么”，不复述“怎么做”）。
     *
     * 引用 MC API：
     *   - net.minecraft.entity.Entity#tick()：服务端每 tick 调用的入口，
     *     本方法由它间接触发；
     *   - net.minecraft.util.math.Vec3d：不可变三维向量，用于速度与位置运算；
     *   - net.minecraft.entity.MovementType：move() 的移动类型参数，决定
     *     碰撞与挤压的处理方式。
     *
     * 端侧/线程：仅逻辑服务端；禁止客户端调用。
     * 参数：@param pitchInput 摇杆俯仰输入，范围 -1.0 ~ 1.0，上仰为负。
     * 返回：@return 本 tick 计算后的合速度（Vec3d，永不为 null）。
     * 副作用：修改实体 velocity 与位置；播放旋翼音效（节流后）。
     *
     * 故障排查：
     *   - 直升机原地抖动：先查客户端是否也在写速度（端侧越权），再查
     *     本方法是否被重复调用；
     *   - 穿墙：确认位移走的是 move(MovementType.SELF, ...) 而非 setPos；
     *   - 起飞后下坠：检查重力补偿项是否在服务端生效，客户端单人生存时
     *     注意集成服务端才是权威端。
     */

2.5 字段注释
    静态常量、注册项、参与物理计算或网络同步的字段必须注释，写明单位、
    取值范围、默认值、是否需要同步。例如：
    /** 最大平飞速度，单位：格/tick（blocks/tick），默认 0.8。 */
    private static final double MAX_SPEED = 0.8D;
    /** 当前旋翼转速，0.0~1.0；通过网络包同步给客户端用于动画与音效。 */
    private float rotorSpeed;

2.6 行内注释
    (1) 魔法数字必须命名为常量并注释含义与单位；确实只出现一次的，在行尾
        注释来源（例如经验值、参考的物理系数）。
    (2) 反直觉写法必须注释原因，例如“此处必须先更新 yaw 再算速度，否则
        转向会滞后一 tick”。
    (3) 绕过 MC 缺陷 / 兼容特定版本的 hack 代码，必须以 // HACK(1.21.1):
        开头，写明问题与未来删除条件。

2.7 “出了问题怎么解决”注释的必写场景（至少覆盖与本类相关者）：
    - 注册类：内容不出现 / 报错“Registry already contains”→ 检查注册名
      重复、注册时机是否在初始化事件内、MOD_ID 是否一致；
    - 实体类：实体不出现、不同步、抖动、穿墙、乘骑错位 → 按 2.4 模板逐项
      排查端侧、移动方式、追踪数据（TrackedData）；
    - 网络包：收不到包 → 检查通道注册方向（C2S/S2S 不匹配）、payload
      id 是否一致、是否在客户端错误地操作服务端状态；
    - 渲染类：黑屏 / 透明 / 模型错位 / 崩溃 → 检查纹理 Identifier 路径、
      @Environment 隔离、渲染线程与矩阵栈状态是否还原；
    - 输入按键：按键无响应 → 检查 KeyBinding 注册、客户端 tick 事件挂载、
      焦点是否在 GUI 界面；
    - 音效：不响或重叠爆音 → 检查声音事件注册、播放端侧、节流条件。

第 3 章  命名规范
--------------------------------------------------------------------------------

3.1 包名：全小写，单数形式；类名 UpperCamelCase；方法与变量
    lowerCamelCase；常量 UPPER_SNAKE_CASE。
3.2 布尔变量 / 方法以 is、has、can、should 开头，例如 isEngineStarted()。
3.3 类名按职责后缀：注册类以 Mod 开头（ModItems、ModEntityTypes）；
    客户端网络收发以 *Networking 结尾；渲染器以 *Renderer 结尾；模型以
    *Model 结尾；网络载荷以 *Payload 结尾。
3.4 禁止缩写成谜（tmp、data1、aaa）；循环计数器 i/j/k 除外。
3.5 不允许使用中文拼音命名，不允许中英混合标识符。


--------------------------------------------------------------------------------
第 4 章  直升机业务代码规范（按模块）
--------------------------------------------------------------------------------

4.1 实体（Entity）
    (1) 直升机实体继承 MC 载具体系（net.minecraft.entity.vehicle 相关基类
        或 net.minecraft.entity.Entity，按实际需要选择，并在类注释中说明
        选择理由）。
    (2) EntityType 通过 EntityType.Builder.create(...).dimensions(...)
        .build() 构造，在 ModEntityTypes 中统一注册；尺寸改动后同步检查
        乘骑位置与碰撞箱。
    (3) 服务端权威：速度、姿态、燃油、伤害、乘降判定只在服务端计算；
        客户端通过 TrackedDataHandler 注册的 DataTracker 字段或网络包接收
        结果，只做表现。
    (4) 每 tick 逻辑拆分清晰：输入采集 → 物理积分 → move() 碰撞 →
        状态同步 → 音效/粒子，各段以注释分段。
    (5) 需要存档的数据在 writeCustomDataToNbt / readCustomDataToNbt 中
        成对读写；读取属于系统边界，必须做范围校验并注释默认值策略。

4.2 物品（Item）
    (1) 物品注册集中于 ModItems，统一使用 Item.Settings。
    (2) 与直升机交互的物品（如钥匙、维修工具）在 useOnEntity / use 方法的
        JavaDoc 中写清交互目标、端侧与成功/失败条件。

4.3 输入与控制（CLIENT）
    (1) KeyBinding 通过 net.fabricmc.fabric.api.client.keybinding.v1
        .KeyBindingHelper 注册；tick 中轮询使用
        ClientTickEvents.END_CLIENT_TICK。
    (2) 按键只产生“意图”，意图经 C2S 网络包发给服务端，客户端绝不直接
        修改实体权威状态。

4.4 网络（Networking）
    (1) 1.21.1 使用自定义载荷体系：载荷为实现
        net.minecraft.network.packet.CustomPayload 的 record，通过
        net.fabricmc.fabric.api.networking.v1.PayloadTypeRegistry 的
        playC2S() / playS2C() 注册编解码器，再用 ServerPlayNetworking /
        ClientPlayNetworking 注册接收器。每处引用都要在注释中写明全限定名。
    (2) 一个载荷 record 对应一个明确动作，字段不可变并记录单位/范围。
    (3) 服务端接收器是系统边界：必须校验玩家是否骑乘对应实体、距离与权限，
        校验失败直接丢弃，必要时记日志；这属于必要校验，不算防御性代码。

4.5 渲染与音效（CLIENT）
    (1) 渲染器、模型、图层全部置于 client 包并标注
        @Environment(EnvType.CLIENT)，通过 EntityRendererRegistry 在
        客户端初始化中注册。
    (2) 渲染中对 MatrixStack、RenderLayer 的状态改动必须成对还原。
    (3) 旋翼动画使用插值后的同步字段，禁止在渲染线程读写逻辑状态。
    (4) 循环音效做距离衰减与节流，禁止每 tick 重复 playSound。


--------------------------------------------------------------------------------
第 5 章  通用代码风格
--------------------------------------------------------------------------------

5.1 缩进 4 空格，不用 Tab；行宽建议不超过 120 字符；花括号采用 K&R 风格。
5.2 import 逐类导入，禁止通配符 import（.*），IDE 格式化时自动整理。
5.3 优先不可变：Vec3d、record、final 字段/局部变量能加则加。
5.4 单一职责：单方法原则上不超过 80 行，超出则按“输入/计算/输出”提取
    私有方法，每个私有方法同样按 2.4 写 JavaDoc。
5.5 可以使用 Stream / Optional，但禁止为炫技写成多层嵌套导致无法调试；
    Optional 禁止用作字段或方法参数。
5.6 废弃代码直接删除（Git 历史可追溯），禁止注释保留、禁止 @Deprecated
    后长期不删。
5.7 提交的代码必须通过 IDE 无警告要求：未使用的导入、变量、方法一律清理。

第 7 章  Mixin 与资源规范
--------------------------------------------------------------------------------

7.1 优先使用 Fabric API 事件；只有事件无法覆盖时才写 Mixin，并在类注释中
    说明“为什么非 Mixin 不可”。
7.2 Mixin 类放入 mixin 包，方法以 @Inject / @Redirect 等注解标明注入点，
    注释写清目标类全限定名、注入位置、取消条件与冲突风险。
7.3 资源文件名全小写；lang 文件至少提供 en_us.json 与 zh_cn.json，键值
    一一对应，不允许残留未翻译键。
7.4 fabric.mod.json 的 entrypoints 区分 main / client，客户端逻辑只进
    client 入口。


--------------------------------------------------------------------------------
第 8 章  测试与验证规范（禁止过度测试）
--------------------------------------------------------------------------------

8.1 分级验证，按改动量选择，不允许加码：
    (1) 小改动（新增方法、改数值、改注释、改资源、修单处逻辑）：只跑
        构建，./gradlew build 成功即视为通过，不做实机、不写单元测试。
    (2) 中等改动（新增实体行为、网络包、渲染、输入链路）：构建通过后，
        允许启动一次游戏做针对性人工验证，验证目标仅限本次改动点，验证
        完毕关闭环境。
    (3) 大改动（物理系统重写、跨端架构调整）：列出 3~6 条核心验证点，
        逐条人工确认，不写长期保留的自动化测试。
8.2 项目不维护 src/test 目录，不保留 JUnit 用例。若为排查问题临时编写了
    测试类、main 方法、调试命令、临时数据包，问题解决后必须立即删除，
    并确认构建产物目录（build/）不作为提交内容（build/ 必须在
    .gitignore 中）。
8.3 禁止生成测试存档、测试截图、测试日志并放入项目；需要留存证据时放在
    项目目录之外。
8.4 不允许为“以防万一”添加无关注销、空实现、占位逻辑——这属于防御性
    代码，按第 0.3 条处理。
8.5 验证失败时先修根因，禁止用注释掉报错代码、加空 catch、跳过任务等
    方式让构建“假通过”。

10.2 README.md 内容（只写“当前版本是什么”）：
     - 模组简介、运行环境（Minecraft 1.21.1 / Fabric 0.19.2 / Java 21）；
     - 安装方法、操作说明（按键表）、当前功能列表；
     - 已知限制（如有）。
     README 不写任何更新记录、不写版本历史。版本变化时只做两件事：
     新功能出现就加入功能列表；新版本删除的功能就从列表中删掉。保持它
     永远只描述“现在”。

10.3 开发手册.md 内容（所有详尽信息的唯一归宿）：
     - 环境搭建、构建与运行、项目结构说明；
     - 注册体系、实体与飞行物理设计、网络协议（每个 payload 字段表）、
       渲染与音效架构、Mixin 清单；
     - 常见问题排查手册、配置项说明；
     - 末尾固定一章「更新日志」，全项目所有版本变化只记录在这里。

10.4 更新日志规则：
     (1) 位置：开发手册.md 最后一章，日志区之后不得再有其他章节；
     (2) 排序：按日期排序，最新版本在最上方；
     (3) 每次发布必须追加，条目格式统一：

     ## v1.2.0 — 2026-10-14
     - 新增：直升机仪表界面（S2C 同步转速/油量）。
     - 修改：最大平飞速度由 0.6 调整为 0.8（格/tick）。
     - 修复：第三人称旋翼动画抖动一帧的问题。
     - 删除：旧版手摇启动物品（已被钥匙物品替代）。

     (4) 分类固定为：新增 / 修改 / 修复 / 删除，每条一句话写清是什么、
         影响什么；同日多次改动合并到同一版本条目。
     (5) 版本号建议采用语义化版本：主版本.次版本.修订号；不兼容的存档
         改动升主版本，新功能升次版本，修复升修订号。

10.5 文档与代码同一次提交完成：代码改了、文档没同步，视为任务未完成。


--------------------------------------------------------------------------------
第 11 章  Git 与提交信息
--------------------------------------------------------------------------------

11.1 分支：main 保持可构建；开发在 dev 或 feature/<功能名> 分支进行。
11.2 提交信息格式：<类型>: <中文简述>
     类型固定：feat（新功能）、fix（修复）、refactor（重构）、docs
     （文档）、chore（构建/杂务）。示例：feat: 增加直升机俯仰控制
11.3 一次提交只做一件事；构建失败的代码禁止提交。
11.4 .gitignore 至少包含：build/、.gradle/、run/、IDE 配置目录
     （.idea/、.vscode/、*.iml）、系统临时文件。
